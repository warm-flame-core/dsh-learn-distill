# 编排规范：长任务、会话结束、队友状态

## 一、DSH 的三种「结束」

| 形态 | 表现 | 能否被唤醒 |
|---|---|---|
| 结束回合 | 一轮回答结束，等用户下一条消息 | 是（用户发消息） |
| 后台任务 | `run_in_background` 起的 job | 是（跑完自动唤醒） |
| 成员 inactive | 队友/子代理没有轮次在执行 | **不区分**「在等任务」与「已死」 |

**结论**：
- 后台任务是唯一「跑完自动唤醒」的机制
- 成员 inactive 是状态描述，不是结果描述
- 「队友 inactive」无法区分「等任务」「没额度」「死了」

## 二、角色与能力

| 角色 | 能主动结束回合 | 结束后能被唤醒 |
|---|---|---|
| Lead | 是 | 是（用户消息 / job 完成） |
| 队友 | 是 | 是（`send_message`） |
| 子代理 | 是 | **否**（不能寻址，只能等完成通知） |

子代理不能主动结束等唤醒——它结束了就是结束了，父代理只能等完成通知。

## 三、阶段分工

| 阶段 | 执行者 | 等待方式 |
|---|---|---|
| 0-2 参数/probe/闸门 | Lead | 同步 |
| 3-4 字幕/纠错 | Lead | 同步（秒级） |
| 5 抽帧 + OCR | Lead + 后台 job | 结束回合等唤醒 |
| 6 对齐 | Lead | 同步 |
| 7 写作 | 队友 | `wait_agent` 同回合循环 |
| 8-9 装配校验 | Lead | 同步 |
| 9' 盲测 | fresh 子代理 | 结束回合等完成通知 |

### 3.1 为什么 Stage 5 用后台 job

| | 后台 job | 队友 |
|---|---|---|
| 跑完自动唤醒 | 是 | 否 |
| 等待期不耗 token | 是 | 否 |
| 状态可查 | 是（job id/status） | 否（inactive 不区分） |
| 能中途干预 | 否 | 是 |

抽帧/OCR 是确定性脚本，不需要干预，用后台 job 最优。

### 3.2 为什么 Stage 7 用队友

写作需要 LLM，不是脚本，无法用 job。
可并行（多讲次），且需要中途干预（写歪了要停），用队友。

## 四、短课 / 长课编排

### 4.1 阈值

| 长度 | 判据 | 编排 |
|---|---|---|
| 短课 | ≤3 讲次 且 ≤2 小时 | Lead 串行 + 子代理写作 |
| 长课 | >3 讲次 或 >2 小时 | Lead 编排 + 后台 job + 团队 |

### 4.2 短课

```
Lead 一个会话串行跑完
  ├─ 确定性阶段同步跑
  ├─ 写作派子代理（每讲次一个，并行）
  ├─ 结束回合等完成通知
  └─ 唤醒后装配校验
```

不建团队（开销不值得）。

### 4.3 长课

```
Lead 编排
  ├─ Stage 0-4：同步
  ├─ Stage 5：起后台 job，结束回合等唤醒
  ├─ Stage 6：同步
  ├─ Stage 7：建团队，每讲次一个任务，队友并行写
  │    └─ Lead 用 wait_agent 同回合循环（不结束回合）
  ├─ Stage 8-9：同步
  └─ Stage 9'：派 fresh 子代理盲测，结束回合等
```

## 五、队友「死没死」判据

### 5.1 设计原则：不让队友等长任务

```
队友只做短任务（≤5 分钟）
  → inactive 只剩「完成」或「死」
  → 用任务板状态区分
```

### 5.2 任务板状态判据

| 任务板状态 | 含义 | 处理 |
|---|---|---|
| `pending` + 无 owner | 没人接 | `send_message` 催 |
| `in_progress` + 有 owner | 在干 | 等 |
| `completed` | 完成 | 继续下一步 |
| `in_progress` 超过 15 分钟无更新 | 疑似卡死 | `interrupt_agent` 后重派 |

### 5.3 心跳字段（兜底）

任务 description 里约定：

```
## 心跳
last_update: <ISO 时间>
state: running | waiting_job | blocked | done
note: <一句话>
```

队友每完成一个子步骤更新一次。Lead 用 `team_task_get` 读。

| 情况 | 处理 |
|---|---|
| `state=running` 且 <5 分钟 | 正常 |
| `state=waiting_job` | 在等后台任务 |
| `state=blocked` | `send_message` 问 |
| 时间戳 >15 分钟无更新 | 疑似死，`interrupt_agent` 后重派 |

## 六、会话结束策略

### 6.1 可以主动结束的情况

| 场景 | 做法 |
|---|---|
| Lead 起了后台 job，只需等它 | 告知用户「已起 job <id>，结束回合等唤醒」 |
| Lead 等子代理 | 告知用户后结束回合 |
| 队友等后台 job | 可以结束回合，job 完成会唤醒它 |

### 6.2 不要结束回合的情况

| 场景 | 做法 |
|---|---|
| Lead 等队友 | `wait_agent` 同回合循环，不结束回合（会丢失循环上下文） |
| 子代理 | 不能主动结束等唤醒 |

### 6.3 结束回合前义务

必须先对用户说明「已发起 <什么>，现在结束本回合等回执」。

### 6.4 状态持久化

写 `_meta/state.json`：

```json
{
  "course": "<id>",
  "goal": "deep_mastery",
  "stage": 7,
  "lectures": [
    {"id": "lecture-01", "status": "done"},
    {"id": "lecture-02", "status": "in_progress", "owner": "writer-02"},
    {"id": "lecture-03", "status": "pending"}
  ],
  "jobs": [{"id": "bash-xxx", "kind": "frames_ocr", "status": "done"}],
  "updated": "<ISO 时间>"
}
```

作用：会话中断能续、结束回合后唤醒能恢复、队友死了知道从哪继续。

## 七、长任务中途干预

| 对象 | 干预方式 |
|---|---|
| 队友 | `interrupt_agent` |
| 后台 job | `job_kill` |
| 子代理 | 不能干预（只能等完成） |

## 八、检查清单

```
□ 长任务用后台 job，不用队友
□ 队友只做 ≤5 分钟的任务
□ 任务板有心跳字段
□ Lead 等队友用 wait_agent 循环，不结束回合
□ Lead 等子代理/job 结束回合，并告知用户
□ 子代理不主动结束等唤醒
□ 结束回合前写 state.json
□ inactive 超 15 分钟无更新 → 判死
```

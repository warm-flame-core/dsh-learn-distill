# 子代理与智能体团队：分工规范

> **本文件每一级都要读**：Lead、队友、子代理都适用。
> 当你从被派者变成派活者（队友再建子代理），同样要遵守本文件。

## 一、机制选型

| | 子代理（`subagent` / `subagent_fork`） | 智能体团队（`spawn_teammate`） |
|---|---|---|
| 出现在 `list_agents` | 否 | 是 |
| 能被 `wait_agent` 等 | 否 | 是 |
| 结果返回方式 | 完成通知带回正文 | `send_message` + 共享任务板 |
| 共享任务/依赖/写范围 | 无 | `team_task_*`（含 `blocked_by`、`write_scopes`） |
| 可中断 | 无 | `interrupt_agent` |
| 可再建下级 | 仅能建子代理 | 仅 Lead 能建队友；队友可建子代理 |

### 选型规则

| 场景 | 选谁 |
|---|---|
| 一次性、单输出、无需协作 | 子代理 |
| 多视角并行、要汇总去重、要中断、要任务依赖 | 智能体团队 |

两种机制都是完整工具集，无只读白名单——只读靠任务书纪律。
两种机制都必须在任务书里限定读取范围与输出格式。

## 二、层级与创建权限

| 层级 | 能建队友 | 能建子代理 | 能用 `wait_agent` |
|---|---|---|---|
| Lead | 是 | 是 | 是（只等成员） |
| 队友 | 否（权限拒绝） | 是 | 是（只等成员） |
| 子代理 | 否（工具不在集内） | 是（到上限即拒） | 否（工具不在集内） |

**两种失败形态不同**：队友侧是「工具在、被 role 拒」，子代理侧是「工具不在集内」。
判断达上限的依据是**工具返回的错误信息**，不是写死的数字。

## 三、两种阻塞等待（核心）

### 3.1 谁等谁、怎么等

| 谁等谁 | 怎么等 | 同回合能否继续干活 |
|---|---|---|
| **Lead 等队友** | `wait_agent` 同回合阻塞循环 | 能。循环 `list_agents` → `team_task_list` → `wait_agent` |
| **Lead 等子代理** | **结束回合**等完成通知 | **不能** |
| **队友等子代理** | 起完可继续做别的；**要结果必须结束回合** | 起时能 / 要结果不能 |
| **队友等队友** | `wait_agent` 同回合阻塞 | 能 |

### 3.2 判据：什么时候必须阻塞

| 情形 | 处理 |
|---|---|
| 下一步的输入依赖该结果 | **硬阻塞**，必须等到 |
| 结果只用于最后汇总 | **软等待**：可做不依赖它的活，但不得生产依赖该结论的交付物 |
| 写范围重叠 / 同一文件 | **必须串行** |

一句话：**「下一步能不能在不知道这个结果的情况下继续」——能就不阻塞。**

### 3.3 什么时候可以并行

| 情形 | 可否并行 |
|---|---|
| 多个独立读任务，结果各自汇总 | 可以 |
| 多个写任务，写范围互斥 | 可以 |
| 多个写任务，写同一文件 | 不可以，必须串行 |
| 下游依赖上游结论 | 不可以，必须阻塞 |

### 3.4 等待期纪律

Lead 等队友时，**只做三件事**：
1. `list_agents` 查状态
2. `team_task_list` 查进度
3. `wait_agent` 阻塞

不产交付物、不读文件、不跑自检。否则会提前生产依赖该结论的交付物，或拿旧结论往下走。

`timedOut` → 回第一步重查。
`noProgress` → 说明没人在跑，去任务板确认完成还是失败。

### 3.5 结束回合前义务

结束回合前必须先对用户说明：「已发起 <什么>，现在结束本回合等回执」。

### 3.6 易错点

| 易错点 | 后果 |
|---|---|
| 子代理用 `wait_agent` | 永远 `no-active-peer` |
| Lead 等子代理时继续干活 | 提前生产依赖该结论的交付物 |
| 等待期读文件/跑自检 | 拿旧结论往下走 |
| 结束回合前没告知用户 | 用户不知道在等什么 |
| 盲测用 `subagent_fork` | 继承父级历史，测试失效 |

## 四、共享任务板（派活的唯一入口）

### 4.1 为什么用任务板

- 任务**可寻址**（有 id），不依赖对话记忆
- 写范围**显式声明**，并发冲突可提前发现
- 依赖关系**可声明**（`blocked_by`），顺序不会搞错
- 进度**可查询**（`team_task_list`），不用反复问

### 4.2 派活标准流程

```
1. team_task_create
   ├─ subject：任务标题
   ├─ description：完整任务书（自足，不依赖对话上下文）
   ├─ write_scopes：本任务会写的文件/目录（互斥，防并发冲突）
   └─ blocked_by：前置任务 id（有依赖时）
2. send_message 通知队友「任务 <id> 已建，请 claim」
3. 队友 team_task_get 拿最新 revision → team_task_update action=claim
4. 队友干活 → team_task_update action=complete
5. Lead 用 team_task_list 查进度，不靠对话追问
```

### 4.3 任务书必须自足

任务板里的 `description` 是**唯一**的任务依据。队友可能没有对话上下文，所以：

| 必须写 | 说明 |
|---|---|
| 工作目录 | 绝对路径 |
| 输入文件 | 完整路径，逐个列出 |
| 输出文件 | 完整路径，明确只写这一个 |
| 格式要求 | 结构、长度、字段 |
| 禁令 | 不得执行命令、不得写其他文件、只读指定文件 |
| 回执格式 | 逐项列出，总长上限 |
| 需澄清处理 | 遇歧义不猜，回执里写明 |

### 4.4 写范围互斥

`write_scopes` 是**目录或文件前缀**，多个任务的重叠就是冲突信号。

```
任务 A: ["courses/x/dist/lecture-01.md"]
任务 B: ["courses/x/dist/lecture-02.md"]     ← 不重叠，可并行
任务 C: ["courses/x/dist/_index.md"]          ← 不重叠
```

重叠时必须拆任务或改串行。并发编辑同一文件**失败是静默的**（每处都回成功，落盘只有一份）。

### 4.5 依赖声明

```
task-01 取字幕
task-02 纠错        blocked_by: [task-01]
task-03 抽帧OCR     blocked_by: [task-02]
task-04 对齐        blocked_by: [task-03]
task-05 写作-01     blocked_by: [task-04]
task-06 写作-02     blocked_by: [task-04]
task-07 校验        blocked_by: [task-05, task-06]
```

`blocked_by` 未完成时，任务不可 claim。

### 4.6 查询与更新

```
team_task_list                      # 全部任务 + 状态 + 归属 + 阻塞
team_task_list --status pending     # 只看未开始的
team_task_list --ready true         # 只看可开工的
team_task_get <id>                  # 拿最新 revision（更新前必做）
team_task_update <id> expected_revision=<rev> action=claim|complete|release|edit
```

更新必须带 `expected_revision`（CAS 前置条件），防止覆盖别人的改动。

## 五、分工原则

| 类型 | 谁做 |
|---|---|
| 取字幕、抽帧、OCR、对齐、校验 | 脚本（Lead 调用） |
| 六栏讲义写作 | 子代理 / 队友（每讲次一个） |
| 盲测复现 | 子代理（fresh 上下文） |
| 参数解析、闸门、最终裁决 | Lead |

## 六、各阶段分工

| Stage | 谁做 | 机制 |
|---|---|---|
| 0 参数解析 | Lead | 自己 |
| 1 probe | Lead | 脚本 |
| 2 代价闸门 | Lead | 问用户 |
| 3 取字幕 | Lead | 脚本（yutto） |
| 4 术语纠错 | Lead | 脚本（glossary_fix） |
| 5 抽帧 + OCR | Lead | 脚本 |
| 6 对齐 | Lead | 脚本 |
| 7 六栏写作 | 队友/子代理 | 每讲次一个；≥5 讲次用团队 |
| 8 装配 | Lead | 脚本 |
| 9 确定性校验 | Lead | 脚本 |
| 9' 盲测 | 子代理 | fresh 上下文 |
| 9'' 术语复核 | 子代理 | 批量 |

## 七、歧义上报

| 层级 | 做法 |
|---|---|
| 队友 → Lead | `send_message` 说明卡点，停下等回复 |
| 子代理 → 父代理 | 无通讯路径，任务书须写「遇需澄清 → 不猜，回执『需澄清』栏写明，该部分不做」 |
| 父代理收到「需澄清」 | 必须处理：补材料重发 / 自己查 / 问用户 |

## 八、达上限时

```
1. list_agents 查现有成员
   ├─ 有 inactive 且任务可续 → send_message 唤醒
   └─ 没有 → 尝试创建
2. 创建被拒
   ├─ 必须项 → 向上级汇报一次，按兜底继续
   └─ 非必须 → 本层自己干，交付声明降级
```

## 九、降级路径

| 情形 | 退路 |
|---|---|
| 子代理回执为空或自报越界 | 检查任务书输出格式，重发 |
| 团队建不出来 | 退回子代理串行 |
| 成员卡住或反复 timedOut | `interrupt_agent` → 退回子代理 |
| `noProgress` 但任务板未完成 | `send_message` 唤醒该成员 |
| 子代理层到顶 | 本层自己干，交付声明降级 |
